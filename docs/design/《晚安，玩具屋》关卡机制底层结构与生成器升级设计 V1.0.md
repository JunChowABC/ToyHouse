# 《晚安，玩具屋》关卡机制底层结构与生成器升级设计 V1.0

## 1. 核心调整

当前玩法不再将关卡理解为：

> 一堆具有 U / D / L / R 朝向的 Toy。

升级为：

> **空间占格系统 + Blocking Graph + Trigger Graph + Release Graph。**

玩家看到的是可爱的玩具堆。

程序真正运行的是一张不断变化的：

**Dependency Graph。**

# 2. Entity 数据结构重构

不建议以后每出现一个新机制就增加一种新的 `archetype_id`。

例如：

- 普通兔子
- 睡觉兔子
- 钥匙兔子
- 抱抱兔子

本质仍然都是：

**1×2 固定方向手动玩具。**

因此建议拆成：

## 2.1 Archetype｜功能原型

只负责最基础的移动规则。

```
ORDINARY
AUTO_EXIT
LARGE
```

分别对应当前：

- 兔子 1×2；
- 小鸭 1×1；
- 鲸鱼 1×3。

现有 MDD 已经明确“功能原型决定占格、操作方式和离场规则，皮肤不改变功能原型”。

## 2.2 Modifier｜状态机制

附着在原有 Toy 上。

```
SLEEPING
HUG_LOCKED
KEY_CARRIER
FROZEN
```

因此：

```
Rabbit_023
archetype = ORDINARY
modifier = SLEEPING
```

仍然是一只普通兔子。

只是当前处于：

> 不可操作的睡眠状态。

## 2.3 Board Entity｜盘面实体

不是需要送回家的 Toy，但参与占格与阻挡。

```
BOX
SPRING
LOCK_BOX
PORTAL
```

这些对象：

- 可以占格；
- 可以阻挡；
- 可以被触发；
- 不计入 Toy Clear Count。

这样不会污染原来的 Toy 原型体系。

# 3. Trigger 统一模型

所有特殊机制统一采用：

```
Source
↓
Event
↓
Condition
↓
Target
↓
Action
```

例如：

```
Rabbit_012
↓
EXIT
↓
Always
↓
Sleeping_Rabbit_031
↓
WAKE_UP
```

表示：

> Rabbit_012 离场后，Rabbit_031 苏醒。

另一个例子：

```
KeyRabbit_08
↓
EXIT
↓
KeyID = GOLD_01
↓
LockBox_02
↓
UNLOCK
```

纸箱：

```
Rabbit_17
↓
COLLIDE
↓
Target = Box_01
↓
Box_01
↓
DAMAGE -1
```

弹簧：

```
Rabbit_25
↓
COLLIDE
↓
Target = Spring_03
↓
Spring_03
↓
PUSH until blocked or exit (沿撞击方向持续滑行；2026-09-30用户修正)
```

以后新增机制原则上都进入这套 Trigger 系统。

# 4. 标准事件类型

第一版建议固定以下事件：

```
ON_EXIT
ON_SHIFT
ON_COLLIDE
ON_OCCUPANCY_CHANGE
ON_UNLOCK
ON_WAKE
ON_PUSH
ON_DESTROY
ON_AUTO_EXIT
```

不要让每个机制自己定义事件名。

# 5. 标准 Action 类型

# 6. 新的完整结算时序

以后玩家点击一个兔子，不再只处理：

> Move → Duck Scan。

统一改成：

```
Player Click
↓
Manual Toy Path Check
↓
Movement Resolution
↓
Collision Resolution
↓
Occupancy Update
↓
Trigger Queue
↓
Mechanic Resolution
↓
Duck Auto Exit Scan
↓
Trigger Queue
↓
Next Duck Round
↓
直到事件队列为空
↓
恢复玩家输入
```

# 7. Event Queue

这是整个机制系统最重要的部分。

建议每次操作建立：

```
EventQueue
```

例如玩家点击 Rabbit_07：

```
01 Rabbit_07 SHIFT
02 Rabbit_07 COLLIDE Box_02
03 Box_02 DAMAGE
04 Box_02 DESTROY
05 OCCUPANCY_CHANGE
06 Duck_11 AUTO_EXIT
07 Duck_12 AUTO_EXIT
08 Duck_11 ON_EXIT
09 SleepingRabbit_28 WAKE
10 OCCUPANCY_CHANGE
11 Duck_19 AUTO_EXIT
12 EventQueue Empty
```

只有：

> EventQueue = Empty

时玩家才能进行下一次操作。

# 8. 为什么必须使用 Queue

否则以后很容易出现这种程序歧义：

兔子撞纸箱
→ 纸箱破坏
→ 小鸭离场
→ 小鸭触发睡眠兔苏醒
→ 苏醒是否应该发生在下一轮小鸭扫描之前？

统一 Queue 后答案明确：

### Phase 1

处理当前 Trigger。

### Phase 2

更新 Occupancy。

### Phase 3

重新扫描所有自动机制。

### Phase 4

产生新 Trigger。

### Phase 5

继续处理。

直到：

```
No Event
```

# 9. Blocking Graph

原来的依赖关系继续保留：

```
A → B
```

含义：

> A 当前阻挡 B。

但建议正式定义为：

```
A --BLOCKS--> B
```

例如：

```
Rabbit_01 --BLOCKS--> Rabbit_17
Rabbit_17 --BLOCKS--> Whale_02
```

# 10. Trigger Graph

新增：

```
A --TRIGGERS--> B
```

例如：

```
Rabbit_08 --EXIT_UNLOCK--> LockBox_01
Duck_12 --EXIT_WAKE--> Rabbit_31
Rabbit_22 --HIT_DESTROY--> Box_03
```

# 11. Release Graph

再单独记录：

```
A --RELEASES--> B
```

它不代表直接触发，而表示：

> A 状态改变后，B 获得可离场条件。

例如：

```
Box_03 --DESTROY_RELEASES--> Duck_18
Duck_18 --EXIT_RELEASES--> Rabbit_40
```

# 12. 最终 Dependency Graph

一张关卡实际上会形成：

```
Rabbit_03
   │
   │ BLOCKS
   ▼
Rabbit_11
   │
   │ HIT
   ▼
 Box_02
   │
   │ DESTROY
   ▼
 Duck_08
   │
   │ AUTO EXIT
   ▼
SleepingRabbit_27
   │
   │ WAKE
   ▼
Whale_04
```

这才是真正应该先生成的“关卡”。

二维坐标只是这张 Graph 的空间实现。

# 14. 第一步：生成 Release Skeleton

例如普通难度：

```
Layer 0    9
Layer 1    8
Layer 2   10
Layer 3   11
Layer 4   12
Layer 5    9
Layer 6    7
Layer 7    4
Layer 8    2
```

这代表玩家不断解开盘面后，每层大致释放多少对象。

不是要求玩家严格按照这一层顺序操作。

它描述的是：

> 盘面的整体释放结构。

# 15. 第二步：插入机制节点

例如 72 Toy 普通难度：

```
Rabbit       55
Duck          8
Whale         5
Sleeping      2
Box           2

```

注意：

Sleeping 不是额外 Toy。

它是 55 个 Rabbit 中的 2 个。

```

```

# 16. Mechanic Density

正式增加一个指标：

```
Mechanic Density
=
Special Mechanic Nodes
/
Total Interactive Nodes
```

建议：

### 低机制密度

```
5%～8%
```

### 中机制密度

```
8%～15%
```

### 高机制密度

```
15%～22%
```

原则上：

> 不建议超过 25%。

否则盘面阅读重点会从“找路径”变成“认规则”。

# 17. Dependency Depth

定义：

> 从一个当前可操作节点开始，到其最终释放目标之间最长依赖链长度。

例如：

```
兔子
↓
纸箱
↓
小鸭
↓
睡眠兔
↓
鲸鱼
```

Dependency Depth：

```
4
```

建议：

### 简单

```
2～3
```

### 普通

```
3～5
```

### 困难

```
5～7
```

不建议常规关超过：

```
8
```

因为玩家已经很难通过视觉建立因果关系。

# 18. Cascade 强度重新定义

之前 Cascade 主要依赖：

> 一次操作释放多少 Toy。

加入机制后不够用了。

正式拆成四个指标：

## 18.1 Cascade Length

一次玩家操作之后：

> 自动产生多少个连续事件。

## 18.2 Cascade Toy Release

这条 Cascade 中：

> 实际离场多少 Toy。

## 18.3 Cascade Mechanic Count

这条 Cascade 中：

> 激活多少特殊机制。

## 18.4 Cascade Depth

事件链经过多少层 Trigger。

例如：

```
兔子 SHIFT
↓
撞弹簧
↓
弹簧移动
↓
Duck ×2
↓
锁盒解除
↓
Duck ×3
```

可以记录：

```
Cascade Length = 8
Toy Release = 5
Mechanic Count = 2
Cascade Depth = 4
```

# 19. Cascade 强度档位

### LOW

主要是：

```
玩家操作
→ 1～2 个自动事件
```

目标：

```
Cascade Toy Release：1～3
Cascade Depth：1～2
```

### MEDIUM

```
玩家操作
→ 机制
→ 自动释放
→ 第二次盘面变化
```

目标：

```
Cascade Toy Release：3～7
Cascade Depth：2～4
```

### HIGH

出现真正的：

> 多阶段连锁。

目标：

```
Cascade Toy Release：6～12+
Cascade Depth：4～6
```

但是 HIGH 不等于：

> 整关一直自动播放。

玩家仍然需要找到关键 Trigger。

# 20. SHIFT Safety 升级

目前编辑器已经有 SHIFT 安全率。

加入机制以后需要升级成：

## Safe SHIFT

SHIFT 后：

> 至少仍然存在一条无道具解法。

## Productive SHIFT

SHIFT 后：

```
Future Release Potential > Before
```

即未来释放能力增加。

## Cascade SHIFT

SHIFT 本身立即触发：

- 纸箱；
- 弹簧；
- 小鸭；
- Unlock；

之一。

## Trap SHIFT

当前看似可以移动，但移动后：

> 无道具 Solver 判定无法清盘。

编辑器显示：

```
SHIFT Opportunities       21
Safe SHIFT                18
Productive SHIFT          11
Cascade SHIFT              5
Trap SHIFT                 3
```

因此：

```
SHIFT Safety Rate
=
Safe SHIFT / SHIFT Opportunities
```

# 21. SHIFT 安全率目标

### 简单

```
≥ 90%
```

允许玩家大胆尝试。

### 普通

```
75%～90%
```

存在一定错误决策空间。

### 困难

```
60%～80%
```

需要认真判断。

但不建议主动设计：

```
< 50%
```

否则会从空间解谜变成大量试错。

# 25. Deadlock 检测

必须增加以下检测。

## 25.1 Blocking Cycle

```
A blocks B
B blocks A
```

且没有外部节点可以解除。

## 25.2 Trigger Cycle

```
A unlock B
B wakes C
C unlock A
```

但 A/B/C 初始全部不可触发。

## 25.3 Missing Trigger

例如：

```
LockBox_01
```

存在，但：

```
KeyID_01
```

不存在。

直接判：

```
INVALID
```

## 25.4 Unreachable Trigger

钥匙存在，但钥匙 Toy 永远无法离场。

同样：

```
INVALID
```

## 25.5 Mechanic Softlock

例如弹簧必须被从左侧撞击才能移动，但所有可以撞它的玩具都位于右侧。

判定：

```
INVALID_MECHANIC
```

# 36. 最终设计原则

后续新增机制都必须回答 6 个问题：

### ① 它改变什么？

Blocking / State / Trigger / Space？

### ② 玩家怎么触发？

仍然应该尽量通过：

> 点击兔子 / 鲸鱼。

### ③ 它是否产生 Occupancy Change？

如果产生，就必须进入统一结算流程。

### ④ 它会触发什么？

必须可以写成 Trigger Edge。

### ⑤ Solver 怎么模拟？

必须存在确定性的状态转移。

### ⑥ Generator 怎么保证它有意义？

不能只是把一个机制随机摆在盘面上。

因此《晚安，玩具屋》的关卡生成原则最终可以固定成一句话：

> **不是先摆 70 个玩具，再判断它好不好玩；而是先设计一张可玩的 Dependency Graph，再把这张图翻译成 70 个玩具组成的二维盘面。**

这条原则继续作为整个关卡系统、机制系统和编辑器的最高约束。
