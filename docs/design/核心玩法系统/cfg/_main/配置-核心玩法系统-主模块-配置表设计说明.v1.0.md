# 1. 配置归属与边界

## 1.1 分层判定

1. 本文档中的配置直接描述《晚安，玩具屋》核心玩法规则，不满足跨三个系统通用、只加行不加字段、语义跨系统一致的 A 层条件，因此不进入项目通用层。
2. 功能原型、皮肤归属、局内基础参数和反馈事件会被核心玩法的多个规则对象引用，属于主模块共享配置 B-M。
3. 关卡盘面、玩具实例坐标、实例方向、单关功能原型启用清单和单关皮肤映射强绑定关卡生产流程，属于关卡系统配置；本文档只定义引用边界，不复制其字段结构。
4. 文案、音频、动画、特效和美术资源主数据应归入项目通用基础表；核心玩法反馈表只引用资源 ID。

## 1.2 唯一真源

- 业务规则唯一来源：主 MDD 第 4 章；
- 配置字段、类型、默认值与约束唯一来源：本文档；
- 既有可调数值、测试值、公式与校验见数值工作簿；本轮道具经济值补充在第 4.3 节，旧工作簿尚未同步，不以旧表覆盖新规则；
- UI 只读取配置结果，不复制字段定义。

# 2. 设计前五项确认

| 问题 | 本系统结论 |
| --- | --- |
| 谁来配置 | 系统策划维护基础参数、功能原型和反馈；关卡策划选择关卡实例与皮肤；数值策划维护测试值；QA 使用验算区 |
| 配置频率 | 基础参数低频；反馈时长与表现资源在原型期高频；功能原型结构低频且受版本控制 |
| 数据特征 | 基础参数为单行密集数据；功能原型和皮肤为少量固定结构；反馈事件为多行条目 |
| 查询方式 | 运行时按 ID 直接引用；编辑与验算以策划可读性优先 |
| 典型场景 | 修改连击时长、替换普通原型皮肤、调整撞击反馈时长、校验同关同功能原型只选一个皮肤 |

## 4.2 策划填写方式

1. 工作簿中只保留一行启用配置。
2. 修改正式值前，先在连击验算区与场景模拟区确认边界结果。
3. 测试数据转为正式值时，同步将工作簿中的来源状态改为“正式”。
4. 未填写数值不得默认为 0；导入前按本表默认值补齐并执行范围校验。

## 4.3 道具参数与存档（2026.09.16 补充）

正式业务值来自主 MDD 第 4.6、7.1 节；以下代码标识用于核对现有实现，不新增未接入的配置表。

| 参数 | 当前标识/载体 | 值 | 来源状态 |
| --- | --- | --- | --- |
| 道具种类 | TOOL_IDS | remove / shuffle / flip | 对应消除、洗牌、翻转 |
| 各道具初始库存 | EMPTY_TOOLS() | 各 0 | 用户确认 |
| 各道具单关使用上限 | TOOL_LIMIT | 各 3 | 用户确认，分别计数 |
| 单个道具价格 | TOOL_PRICE | 100 金币 | 用户确认 |
| 新玩家初始金币 | loadProfile() 的 coins | 0 | 暂设，待用户确认；不得视为正式经济值 |
| 存档键 | SAVE_KEY | toyhouse-economy-v1 | 当前浏览器本地实现 |
| 消除/洗牌/翻转目标数 | 各道具执行逻辑 | 2 / 5 / 1 | 原有效果延续；目标不足及有效对象见主 MDD |

| 存档字段 | 用途与约束 |
| --- | --- |
| coins | 非负安全整数；购买时验证余额并扣 100，不能透支 |
| inventory | 按 remove/shuffle/flip 分别保存非负安全整数；成功生效扣 1 |
| levelUses | 按关卡 ID，再按道具 ID 保存 0～3 次；跨重开、退出、刷新保留，新关独立计数 |
| rewardIds | 保存奖励来源＋唯一奖励 ID，重复回调不重复发放 |

后续奖励接入使用 window.toyhouseRewards.grant，source 为 task / achievement / rewarded_ad；coins 与 tools 数量必须为非负安全整数。仅已预留接口，不表示平台系统上线；具体调用说明见[道具实现说明](../../../../../art/tool-economy.md)。

资源和标题引用：本轮接入 toyhouse-gameplay-layered-v5.psd 的切片，兔子坐姿按四方向旋转；标题名称来自[关卡标题表](../../../../../art/level-titles.json)，展示格式由 UI 统一为“第01关·月光敲敲窗”。不修改原关卡逻辑布局来适配显示尺寸。

校验覆盖：库存 0/1、金币 99/100、次数 2/3、无有效目标、买后取消、重复回调、同关重开/刷新、新关独立计数。道具使用上限与库存严格分离，发奖不得提高本关上限。

# 10. 配置约束与自动校验

| 约束 | 影响表 | 校验结果 |
| --- | --- | --- |
| 主键唯一且不可复用 | 全部 | 重复即不允许导出 |
| 所有引用 ID 必须存在 | 皮肤、反馈、关卡引用 | 引用断裂即不允许导出 |
| 每个功能原型恰好一个默认皮肤 | 皮肤 | 0个或多于1个均不通过 |
| 同关同功能原型只能映射一个皮肤 | 关卡系统 | 多皮肤映射不通过 |
| 皮肤所属原型必须与关卡映射原型一致 | 皮肤、关卡系统 | 不一致不通过 |
| 连击时间必须大于0 | 基础参数 | 不满足不通过 |
| 离场最短时长不得大于最长时长 | 基础参数 | 不满足不通过 |
| 撞击反馈触发延时必须为0 | 反馈 | 非0不通过 |
| 小鸭必须不可点击且使用自动离场规则 | 功能原型 | 不满足不通过 |
| 兔子与鲸鱼必须固定方向且可点击 | 功能原型 | 不满足不通过 |

# 11. 三组完整配置示例

## 11.1 标准场景：三原型默认皮肤

1. `core_play_base_cfg` 使用默认正式值与测试反馈值。
2. 关卡启用 1001、1002、1003。
3. 单关皮肤映射为 1001→2001、1002→2002、1003→2003。
4. 验证结果：三种皮肤归属正确，同原型无重复映射，连击边界为严格小于8秒。

## 11.2 边界场景：只使用普通兔子

1. 关卡只启用 1001。
2. 单关皮肤映射只配置 1001→2001。
3. 不配置小鸭和鲸鱼实例，不需要填充无意义的占位行。
4. 验证结果：允许一关只使用一种功能原型；小鸭自动连锁不触发。

## 11.3 复杂场景：普通原型换成玩具熊

1. 新增皮肤 2011“玩具熊”，所属功能原型为1001，四方向资源模式为1，默认标记为 false。
2. 关卡普通原型映射为1001→2011，小鸭和鲸鱼仍映射2002、2003。
3. 本关不得再出现1001→2001的兔子映射。
4. 验证结果：同功能原型只有玩具熊一种皮肤；玩具熊仍占1×2并使用固定方向直线规则。

# 12. 策划配置工作流

1. 在工作簿《总览》中查看正式值、测试值、待确认项和配置覆盖矩阵。
2. 需要新增外观时，先在“功能原型与皮肤”Sheet 的皮肤区新增一行，并从下拉列表选择所属功能原型。
3. 需要调整反馈节奏时，在“受阻与撞击反馈”Sheet 修改测试值，再到“连击”或对应验算区检查结果。
4. 关卡策划在关卡系统配置中只选择有效的功能原型 ID 与皮肤 ID，不复制功能规则。
5. 保存前检查《总览》错误扫描、默认皮肤唯一性、引用完整性和同关单皮肤校验全部为“通过”。
6. 导出时排除标记为“计算”“校验”“不导出”和“来源状态”的列。

# 13. 验收清单

- [ ] 配置表归属为 B-M，未污染项目通用层；
- [ ] 同一字段结构只在本文档定义一次；
- [ ] 功能原型、皮肤、反馈、枚举职责单一；
- [ ] 枚举使用整数值，引用使用 ID；
- [ ] 所有引用链可追溯且无循环；
- [ ] 每个功能原型恰好一个默认皮肤；
- [ ] 同关同功能原型只能选择一个皮肤；
- [ ] 正式数值与测试数据明确分离；
- [ ] 已提供标准、边界、复杂三组示例；
- [ ] 已说明默认值、未填写处理与策划配置流程；
- [ ] 工作簿公式、下拉验证与错误扫描全部通过。
