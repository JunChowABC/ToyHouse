# MDD 模版 v1.6

> - 从“程序规格说明书式写法”调整为“策划需求说明式写法”。

# 写作原则

## 1. 文档定位：MDD 是策划规则文档，不是程序设计文档

MDD 的核心任务是让策划、程序、UI、QA 能够快速看懂：

- 玩家从哪里看到 / 进入这个功能；
- 玩家可以做什么；
- 满足什么条件时发生什么结果；
- 不同状态下显示什么、能不能点、点了之后发生什么；
- 哪些规则由什么配置控制；
- 哪些结果会修改玩家数据；
- 哪些特殊情况需要明确业务处理。

MDD **不负责描述程序内部如何实现**。

### 禁止主动写入的技术实现内容

除非来源文档或用户明确要求，否则正文不得出现以下实现层内容：

- Manager / Controller / View / Service / Model 等代码架构；
- 协程、线程、异步回调、请求锁、取消令牌；
- 缓存、对象池、实例生命周期、资源引用计数；
- 射线检测、碰撞检测实现方式、寻路算法；
- 内存释放顺序、资源加载回调顺序；
- 具体类名、函数名、代码调用链；
- “程序应该用 XX 技术实现”。

代码或现有工程仅可用于**核对已有配置名、旧功能事实或已存在规则**，不得把代码结构反推成新的策划规则写入 MDD。

---

## 2. 来源事实优先，正式数值与测试数据分离

1. 用户、GDD、现有 MDD、配置表、已确认策划说明中的内容，优先级最高。
2. 来源已经给出明确规则或已经确认的正式数值时，必须保持原意，不得为了“更完整”自行改写或重新拍值。
3. **当策划没有主动提供或确认正式数值，但功能需要具体数值才能完成原型、开发联调或 QA 测试时，AI 应先给出一版可跑通的测试配置，而不是全部留空。**
4. AI 自行补充的测试数值必须逐项标注 `[测试数据]`，不得与正式数值混写，也不得描述为“正式配置”“锁定值”“最终值”。
5. 测试数据应满足以下要求：
   - 能支撑主流程正常跑通；
   - 数值之间不存在明显自相矛盾；
   - 只补当前功能测试真正需要的参数，不为了显得完整而扩展一整套数值体系；
   - 优先使用简单、易调、易验证的整数或常规区间。
6. **若缺少的不是“具体数值”，而是会改变玩法结果的设计决策，则不得用测试数据替代，应保留 `[待确认：具体内容]`。**
7. 正式数值确认后，应直接替换对应测试数据，并删除 `[测试数据]` 标记。
8. **禁止为了让文档看起来完整而消灭所有待确认项，也禁止把测试数据包装成正式设计结论。**

### `[测试数据]` 与 `[待确认]` 的使用边界

- `[测试数据]`：规则已经明确，只是策划尚未给出最终参数；为了让功能可以先开发、联调、测试，需要先填一个临时值。
- `[待确认]`：规则本身还没有定，存在多个会改变玩家体验或业务结果的方案，AI 无权替策划做决定。

错误示例：

- 来源只说“支持缩放”，AI 写“最小 0.8 倍、最大 1.5 倍”，但未注明这些是临时测试值。
- 来源没有确认“退出预览后是否保留上次镜头位置”，AI 自行决定“不保留”，再标成 `[测试数据]`。这是规则决策，不是数值测试项。

正确写法：

- 支持双指缩放；最小缩放：0.8 倍 `[测试数据]`；最大缩放：1.5 倍 `[测试数据]`。
- 单次预览最多展示 2 名临时角色 `[测试数据]`。
- 退出预览后是否保留上次镜头位置：`[待确认]`。

> 说明：少量测试数值应直接写在对应业务规则或配置字段旁，不需要为了这些临时值额外生成完整的“数值设计章节”。

## 3. 策划信息密度优先

MDD 要做到“信息足够，但不把简单功能写复杂”。

### 强制规则

1. 一条只写一个事情。
2. 能用 1～3 行讲清楚，不扩写成大段解释。
3. 没有实际设计内容的章节不要生成。
4. 不机械输出“本系统不涉及……”“不适用……”。
5. 不为凑章节完整度增加奖励、概率、状态机、异常矩阵、性能指标等内容。

---

## 4. 规则唯一归位（强制）

**同一条规则只能在最适合的位置完整写一次。**

其他章节如果必须提到，只写引用，不得换一种说法重复展开。

### 归位原则

- **开启 / 入口是否显示** → 第 3 章。
- **业务规则、条件、结果、数据变化** → 第 4 章。
- **界面上显示什么、按钮怎么表现、点击后界面怎么变化** → 第 5 章。
- **配置字段结构** → 第 6 章。
- **数值模型 / 公式 / 经济节奏** → 第 7 章。
- **奖励和消耗本身** → 第 8 章。
- **跨系统依赖** → 第 9 章。

例如：

- 第 4 章已经写“材料不足时不可升阶”，第 5 章只需要写“材料不足时数量显示为红色；点击【升阶】提示【材料不足】”，不要重新解释完整升阶条件。

---

## 5. 按“玩家实际接触的对象”组织规则

系统规则默认围绕玩家能理解的业务对象拆分，例如：

- 入口
- 列表
- 玩法入口
- 升阶
- 突破
- 奖励领取
- 角色互动
- 家具互动
- 活动时间
- 排序
- 红点
- 熔炼

禁止优先按程序处理阶段拆成：

- 请求创建
- 模式切换
- 资源初始化
- 对象创建
- 数据同步
- 回调清理

除非这些阶段本身就是玩家可感知、需要策划定义的玩法阶段。

## 6. 图文贴合：界面规则必须围绕界面图就地写

凡是有界面的系统：

1. 先放当前界面的截图、原型图、线框图或占位图；
2. 再按照图中的实际区域 / 控件，自上而下或从左到右写规则；
3. 同一控件的显示、状态、点击、反馈尽量写在一起；
4. 不把一张界面的内容强拆成“结构 / 状态 / 红点 / 弹窗 / 表现”五六个固定章节。

推荐风格：

```text
[界面图]

1、左侧列表
1）显示……
2）排序……
3）点击后……

2、右侧详情
1）显示……
2）若……则……

3、【升阶】按钮
1）材料足够时……
2）材料不足时……
```

## 7. 界面关系图强制规范

当模块存在多个页面、弹窗、子页或条件分支时，MDD 不能只分别描述每个页面，还必须先让读者看懂**这些页面之间怎么串起来**。

### 强制触发条件

满足以下任一条件时，必须提供界面关系图：

1. 模块内存在 **2 个及以上独立页面 / 弹窗 / 子页**；
2. 存在多个入口，且不同入口进入同一页面或不同页面；
3. 存在【确认 / 取消 / 关闭 / 返回】等不同回退路径；
4. 存在成功 / 失败 / 条件不足 / 已完成等界面分支；
5. 存在首次进入、引导、特殊状态页等独立跳转；
6. 仅靠分散文字难以快速理解完整交互链路。

### 关系图必须表达的内容

至少包含：

- 从哪个入口进入；
- 进入哪个主页面；
- 可以继续进入哪些子页 / 弹窗；
- 关键按钮或操作触发什么跳转；
- 关闭、取消、完成后回到哪里；
- 必要的条件分支与特殊去向。

### 推荐表达方式

优先级如下：

1. **真实原型 / 游戏截图拼接 + 箭头 + 触发文字**：优先使用，最接近策划实际评审方式；
2. **评审稿式 SVG 关系图**：当来源没有完整原型、但需要补一版可评审的图稿时，可产出“多图拼接 + 箭头 + 结论说明”的 SVG；
3. Figma / 墨刀 / Axure 等原型流程关系截图；
4. 暂无原型时，使用 Mermaid 或其他流程图临时表达，后续再替换。

关系图中的箭头应尽量标明触发动作，例如：

- 点击【入口】；
- 点击【确认】；
- 点击【关闭】；
- 达成条件后；
- 领取完成后。

### 禁止事项

- 禁止只有单页原型，没有完整页面跳转关系；
- 禁止只画“进入”，不画返回 / 关闭 / 完成后的去向；
- 禁止把系统业务流程图直接当作界面关系图；
- 禁止关系图与第 5 章分界面规则出现互相矛盾的跳转。

> 界面关系图解决“页面之间怎么走”；单页界面图解决“这个页面上有什么”。两者不能互相替代。

### 评审稿式 SVG 原型图补充规范

当来源没有最终 UI 稿，或需要在 MDD 中补一版便于评审、沟通、开发对齐的可视化稿件时，可以使用 SVG 原型图。

SVG 原型图分为两种：

1. **关系评审稿式 SVG**：用于表达多页面、多弹窗、多分支之间的跳转关系；
2. **单页评审稿式 SVG**：用于表达某一个页面内部的布局、关键按钮、重点区域与交互说明。

### 关系评审稿式 SVG 的推荐写法

应尽量做到：

- 一张图内并列放出多个页面 / 弹窗缩略图；
- 使用箭头连接关键跳转路径；
- 箭头旁标注触发动作，如“点击【预览】”“点击【关闭】”“加载完成后”；
- 对失败分支、状态分支、返回路径单独划区；
- 图下补 3～5 条结论说明，概括这条链路最重要的规则。

推荐结构示意：

```text
[来源界面缩略图] --点击【预览】--> [加载状态缩略图] --加载完成--> [预览主界面缩略图] --点击【关闭】--> [返回来源界面]
                                             \--加载失败--> [失败提示]
```

### 单页评审稿式 SVG 的推荐写法

应尽量做到：

- 一个页面只放一张较大的主体图；
- 用红框 / 高亮框标记重点区域；
- 用引线 + 序号说明关键按钮、列表、状态区、提示区；
- 图下补“页面规则摘要”，把最关键的 2～4 条规则收束一下。

推荐结构示意：

```text
[主页面大图]
1. 套装标题
2. 场景区域
3. 引用家具高亮
4. 【关闭】按钮
5. 家具占用提示

[页面规则摘要]
- 从单件家具进入时显示高亮；
- 家具被角色占用时点击只显示提示；
- 点击关闭后直接返回来源界面。
```

### SVG 原型图使用边界

- SVG 原型图是**策划表达工具**，不是最终 UI 定稿；
- 允许为了表达关系和结构做概括性绘制，但不能创造正文里没有的业务规则；
- SVG 图中的按钮名称、状态名称、返回路径必须与正文一致；
- 若正文与 SVG 冲突，以修改文档为准，不允许放任两边不一致。

## 8. 配置引用就地写

当某条规则由现有配置控制时，应直接在规则旁写明：

- `（读取 equip_cfg-装备升阶sheet-消耗）`
- `（读取 agenda_cfg-限时活动配置sheet-时间id）`

原则：

1. 配置引用用于告诉开发 / 策划“该规则的数据从哪里来”。
2. 不因为引用了配置就继续解释程序如何读取。
3. 第 6 章负责配置结构，不重复第 4 / 5 章的业务规则。

---

## 9. 名词纯净化

- 正文、列表、规则描述中，严禁在中文名词后用括号备注英文变量名。
- 英文变量名只允许出现在【核心公式】或【配置表结构】中。
- 能用中文业务名词表达时，不使用代码变量或技术术语。

错误：`当前挑战次数 (DailyCount)`

正确：`当前挑战次数`

---

## 10. 状态机、流程图不是默认必写项

只有当不用它们会明显降低理解效率时才写。

### 状态机建议使用条件

满足以下任一情况再考虑：

- 状态 ≥ 4 个，且状态之间存在明确转换；
- 活动存在准备期 / 进行期 / 结算期 / 展示期；
- 领取、过期、补发等状态关系复杂；
- UI 多个区域高度依赖同一套状态。

否则直接在对应规则或界面对象下写清即可。

### 流程图建议使用条件

- 多阶段副本；
- 跨服 / 匹配 / 组队流程；
- 长事件链；
- 规则仅靠文字难以快速理解。

简单系统禁止为了“看起来专业”强行补状态机或流程图。

---

## 11. 异常只写“业务结果异常”，不写程序内部异常

MDD 需要关心的是：异常发生后玩家数据、奖励、状态、操作结果怎么办。

适合写：

- 领奖时背包满；
- 付费操作中断；
- 活动结束时玩家仍在玩法中；
- 重复领取；
- 断线后是否保留已产生的业务结果；
- 配置缺失导致无法正常展示 / 发奖时的业务兜底。

不适合写：

- 某资源异步加载晚回来；
- 某回调已经取消；
- 对象释放后再次创建；
- 内存释放失败；
- 某管理器栈顶状态异常。

---

## 12. 允许“工作态策划文档”存在

如果来源本身存在尚未确认的内容，应保留策划工作状态，例如：

- `[待确认：该字段是否已有配置]`
- `[待确认：该状态是否需要独立提示]`
- `[需要程序确认：现有配置是否支持直接跳转]`

不得把所有问题都擅自补成确定答案。

# 1. 模块概述

## 1.1 模块概括

**[AI_GUIDE_START]**

### 要写什么

用 2～5 条说明本次新增 / 修改了什么。

优先写：

- 新增了什么功能；
- 原功能改了什么；
- 玩家操作或入口有什么变化；
- 关键规则有什么变化。

### 怎么写

- 每条一句；
- 不解释实现；
- 不在这里提前展开详细规则。

示例：

## 1.2 设计目的

**[AI_GUIDE_START]**

### 核心要求

设计目的只回答：**为什么要做这个功能 / 这次改动希望解决什么。**

### 写法

- 默认 1～3 条；
- 用自然的策划语言直接写目的；
- 不强制拆成“问题：……目标：……”；
- 不强制覆盖体验、数值、留存、商业化四个维度；
- 只有来源确实存在对应目标时才写；
- 不在设计目的中硬塞“性能目标”“数据隔离目标”“技术目标”。

### 推荐句式

- 让玩家可以……
- 增加……的成长空间。
- 降低玩家理解……的成本。
- 更直观地展示……
- 补足……阶段的长期追求。

**[AI_GUIDE_START]**

1. 入口来源；
2. 主页面；

4. 关键按钮或操作对应的跳转方向；

- 左侧放正常流程；

- 每个页面用小图或缩略图表示；
- 箭头旁标注触发动作；

- 点击【预览】；

# 13. 验收标准

> 验收项应能直接对应正文规则，不新增正文不存在的设计要求。

## 13.1 功能验收

按功能对象列关键结果，例如：

- 满足升阶条件时可正常升阶；
- 材料不足时不扣材料、不改变装备阶数，并提示正确原因；
- 达到最高阶后界面显示最高阶状态；
- 可进化时箭头和红点按规则显示，条件消失后同步消失。

## 13.2 UI / 交互验收 [有界面时]

- 触发界面关系图条件时，第 5 章已提供完整关系图；

- 界面显示内容与第 5 章一致；
- 默认选中、排序、状态切换正确；
- 特殊返回路径正确；
- 已定义的提示、红点、角标表现正确。

## 13.3 性能 / 体验指标 [只有来源有明确指标时]

- 界面打开 ≤ 1 秒；
