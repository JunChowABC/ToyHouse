# 动作-ADD 美术需求模版规范 v1.5

## 写作原则

## 0. 文档定位

ADD（Art Design Document，美术需求文档）用于把策划、交互、数值、关卡包装等需求，整理成可直接交付给 AI、美术、动效、UI、场景包装协作方的标准化需求文档。

本文档聚焦 **动作模块**，覆盖角色 / 怪物的待机、移动、攻击、受击、登场、庆祝、失败等所有动作资源的需求书写规范。

ADD 的目标不是"描述系统功能"，而是把需求翻译成**可直接拆任务、可直接开制作、可直接验收**的美术语言。

ADD 需要解决四件事：

1. 让动画师明确知道"要做什么动作"
2. 让需求方明确知道"哪些动作资源必须交付"
3. 让协作方明确知道"哪些内容属于动作、哪些属于特效"
4. 防止来源文档中的角色状态、动作类型、交付格式要求被遗漏

## 1. 核心原则

### 1.1 ADD 是"来源文档的美术覆盖映射文档"

ADD 不是自由整理文档，而是来源 MDD 文档中所有需要美术承接内容的覆盖映射文档。

在生成 ADD 前，必须先从以下来源中提取美术对象：

- UI 交互说明
- 美术元素资产清单
- GDD
- MDD
- 其他经确认的需求文档

未进入覆盖清单的对象，不允许在 ADD 中被默认省略。

### 1.2 ADD 的重点是"长什么样 / 怎么演"，不是"能做什么"

ADD 中的动作需求描述应优先回答：

- 这是谁的动作
- 属于哪个类型（基础 / 战斗 / 表现）
- 用在什么场景
- 动作整体怎么演
- 节奏和幅度是什么感觉
- 是否循环 / 是否带位移
- 至少需要几套

禁止把 ADD 写成偏功能说明的文档。

### 1.3 一条需求只描述一个动作资源

不要把多个动作混在一条里写。每一条动作需求对应一个可独立交付的动作资源。

### 1.4 动作需求不写标签，写动画师能直接开做的内容（动作专属原则）

动作需求不要只写"待机动作""攻击动作""Boss 出场动画"这种标签式名称，而要直接写成动画师拿到就能开做的内容。

每条动作需求至少要在同一行里写清：

- 这是谁的动作
- 动作属于基础 / 战斗 / 表现中的哪一类
- 用在什么场景
- 动作整体怎么演
- 节奏和幅度是什么感觉
- 是否循环
- 是否带位移
- 是否需要配合表情 / 特效 / 武器
- 至少需要几套
- 最终怎么交付

**不合格写法：**
- 待机动作
- 攻击动作
- Boss 出场动画
- 做一个庆祝动作
- 失败动作，自然一点

**合格写法：**
- 做主目标角色的基础待机动作，整体气质偏轻松可爱，身体有轻微呼吸起伏，头部和四肢可有小幅自然摆动，适合长时间循环播放。
- 做蜜蜂敌人的基础攻击动作，整体要体现快速逼近和连续压迫感，起手短、命中点明确，不做笨重停顿。
- 做 Boss 的登场动作，整体要有压迫感和正式亮相感，建议先压低姿态，再抬头、展开主体肢体并完成一次带停顿的亮相 pose。

### 1.5 复用不等于不用写

若某动作在当前系统中有独立触发场景、独立状态要求，即使是复用已有功能，也必须写进 ADD。只有"完全复用旧资源、当前系统无新增动作要求"时，才允许写"完全复用，不展开"。

### 1.6 动作资源的覆盖边界

**动作-ADD 不收录：**

- UI 动画（页面切换、按钮弹入等）→ 由 UI 动效承接
- 道具动画（道具浮动、旋转等）→ 由特效或原画承接
- 场景动画（背景元素动效）→ 由原画或特效承接
- 机关动画（机关开启/关闭等）→ 由原画或特效承接

**动作-ADD 收录：**

- 角色 / 怪物的骨骼动画
- 角色待机、移动、攻击、受击、死亡、登场、庆祝等动作状态
- 需要动画师独立制作的动作资源

## 2. 适用范围

动作-ADD 覆盖以下资源类型：

- 待机动作
- 行走 / 跑步 / 飞行
- 攻击 / 技能 / 受击 / 死亡
- 登场 / 胜利 / 失败 / 受惊 / 庆祝
- 剧情反应 / 结算展示 / 特写动作

所有动作统一收录在同一张表中，通过"分类"字段区分：

- **基础**：角色常规功能性动作，如待机、行走
- **战斗**：角色攻击、受击、死亡等战斗状态动作
- **表现**：角色剧情、结算、登场等表演性动作

**不在动作-ADD 覆盖范围内：**

- 图标资源 → 写进原画-ADD
- 页面背景 → 写进 UI-ADD
- 特效资源（序列帧/粒子）→ 写进特效-ADD
- UI 动画 / 道具动画 / 场景动画 → 不在任一动作 ADD 中

## 3. 生成 ADD 前的强制步骤

### 3.1 先建立《角色与怪物清单》（强制）

在正式建立《ADD 覆盖总表》前，必须先把来源文档中的所有角色和怪物列出来，作为动作需求的归属基础。

#### 表结构建议

| 角色/怪物名称 | 角色类型   | 来源文档 | 是否有动作需求 | 动作数量估算 |
| ------------- | ---------- | -------- | -------------- | ------------ |
| 主目标角色    | 被保护对象 | 资产清单 | 是             | 4套          |
| 蜜蜂          | 危险对象   | 资产清单 | 是             | 2套          |
| Boss          | 特殊敌人   | GDD      | 是             | 3套          |

#### 强制规则

- 所有在来源文档中出现的角色 / 怪物，都必须先进入角色清单，再确认其动作需求范围
- 未进入角色清单的对象，不允许在 ADD 中被遗漏

### 3.2 然后建立《ADD 覆盖总表》

在正式写 ADD 正文前，必须先整理覆盖总表。

#### 表结构建议

| 来源文档 | 角色/怪物 | 动作名称   | 动作分类 | 触发场景     | 是否已覆盖 |
| -------- | --------- | ---------- | -------- | ------------ | ---------- |
| 资产清单 | 主目标角色 | 待机       | 基础     | 局内常驻     | 是/否      |
| 资产清单 | 主目标角色 | 成功庆祝   | 表现     | 成功结算触发 | 是/否      |
| 资产清单 | 蜜蜂      | 攻击动作   | 战斗     | 攻击目标时   | 是/否      |
| GDD      | Boss      | 登场       | 表现     | 首次出场     | 是/否      |

#### 目的

用于防止：

- 漏某个角色的某类动作
- 漏结算动作
- 漏登场动作
- 新版本新增角色动作未同步进 ADD

### 3.3 再建立《资源层级覆盖矩阵》

#### 表结构建议

| 动作类型       | 是否必须                 | 当前项目是否有 | 对应角色举例     | ADD 是否有对应章节 |
| -------------- | ------------------------ | -------------- | ---------------- | ------------------ |
| 基础待机       | 有可见角色则必须         | 是/否          | 主目标角色、蜜蜂 | 是/否              |
| 基础移动       | 有移动逻辑的角色必须     | 是/否          | 蜜蜂巡逻         | 是/否              |
| 战斗攻击       | 有攻击行为的敌人必须     | 是/否          | 蜜蜂攻击         | 是/否              |
| 战斗受击/死亡  | 有受击/死亡状态必须      | 是/否          | 主目标角色失败   | 是/否              |
| 表现登场       | 有特殊登场演出必须       | 是/否          | Boss 登场        | 是/否              |
| 表现庆祝/失败  | 有结算动作则必须         | 是/否          | 主目标角色成功   | 是/否              |

## 4. 通用字段规范

### 4.1 动作需求字段

| 字段                  | 是否必填 | 说明                                        |
| --------------------- | -------- | ------------------------------------------- |
| 资源ID                | 必填     | 便于追踪，建议 ANI-XXX 格式                 |
| 分类                  | 必填     | 基础 / 战斗 / 表现                          |
| 模块                  | 必填     | 所属角色或怪物名称                          |
| 资源名称              | 必填     | 动作名称（可交付对象名称）                  |
| 需求描述              | 必填     | 写清是谁的动作、怎么演、节奏、幅度          |
| 状态拆分 / 最少套数   | 必填     | 至少需要几套                                |
| 循环方式              | 必填     | 循环 / 单次                                 |
| 位移要求              | 必填     | 原地 / 可带小幅位移 / 带明显位移            |
| 绑定内容 / 关键点     | 建议必填 | 是否需要配合表情/特效/武器，关键帧节点       |
| 参考图                | 建议必填 | 参考图 / 参考视频，只能辅助，不能替代描述   |
| 输出要求              | 必填     | Spine / 骨骼动画 / 序列帧 / 视频参考 等     |
| 备注                  | 可选     | 优先级、首尾衔接要求、联调要求              |

## 5. 图标与背景资源归属说明

本章为协作边界说明，动作-ADD **不承接**图标、背景和特效资源。

- 货币、道具、奖励等图标 → 写进原画-ADD
- 页面背景 / 弹窗遮罩 → 写进 UI-ADD
- 特效（序列帧/粒子/Shader）→ 写进特效-ADD

如果某个动作需要"动作 + 叠加特效"，则：

- 动作部分写进动作-ADD
- 特效部分写进特效-ADD
- 在动作需求的"绑定内容 / 关键点"字段中标注特效触发帧

## 6. 文档标准结构

推荐动作-ADD 按以下结构写：

### 6.0 文档基本信息

#### 写什么

- 项目名
- 系统名 / 模块名
- 文档版本
- 日期
- 负责人
- 来源文档

#### 怎么写

只写客观信息，不写长段说明。来源文档建议写到具体文档名，而不是只写"策划文档"。

#### 例

- 项目：画线救狗
- 系统：核心玩法系统
- 文档版本：v1.0
- 更新时间：2026-03-24
- 负责人：XXX
- 来源文档：《给美术的关卡元素资产需求清单 v2（整合版）》

### 6.1 ADD 覆盖总表（强制）

#### 写什么

- 角色与怪物清单
- 来源映射表
- 动作层级覆盖矩阵

#### 怎么写

先把来源文档里的所有角色 / 怪物列出来，再逐一确认动作需求范围；最后检查动作资源层是否完整覆盖。

### 6.2 需求概述

#### 写什么

- 本次需求目标
- 需求范围
- 不在本次范围内的内容
- 风格基准
- 复用说明

#### 例

本次需求目标：整理核心玩法首发版动作需求，供动画师直接拆任务。

需求范围：包含主目标角色全状态动作、蜜蜂攻击动作、Boss 登场动作。

不包含：皮肤换装动作、活动专属动画。

风格基准：轻卡通，动作读形清楚，战斗动作起手短、命中点明确。

复用说明：如动作复用已有资源，但当前系统有独立触发要求，仍需写入 ADD。

### 6.3 资源分类总览

#### 写什么

概括本次动作-ADD 涉及的角色数量和动作总量。

#### 例

| 角色/怪物 | 动作套数 | 涵盖类型          |
| --------- | -------- | ----------------- |
| 主目标角色 | 4套      | 基础 + 战斗 + 表现 |
| 蜜蜂      | 2套      | 基础 + 战斗       |
| Boss      | 3套      | 战斗 + 表现       |

## 7. 动作需求（核心章节）

> - **模块目标**
>
> 把需要由动画美术承接的角色 / 怪物动作资源，拆成可直接发动画制作的需求。
>
> - **所有动作需求统一使用同一张表管理，不再拆分"基础状态动作 / 战斗动作 / 表现动作"小节。**
> - 所有动作需求均通过表中"分类"字段区分类型，分类建议使用：
>   - 基础
>   - 战斗
>   - 表现
> - 循环、位移、绑定内容、输出方式等要求，统一写进动作表对应字段中，不单独再写"动作交付补充要求"章节。
>
> - **本章节不收录：**
>   - UI 动画
>   - 道具动画
>   - 场景动画
>   - 机关动画

### 7.1 写什么

本章节用于整理角色 / 怪物相关的动作资源需求，包括但不限于：

- 待机
- 行走 / 跑步 / 飞行
- 攻击 / 技能 / 受击 / 死亡
- 登场 / 胜利 / 失败 / 受惊 / 庆祝
- 剧情反应 / 结算展示 / 特写动作

### 7.2 怎么写

动作需求不要只写"待机动作""攻击动作""Boss 出场动画"这种标签式名称，而要直接写成动画师拿到就能开做的内容。

每条动作需求至少要在同一行里写清：

- 这是谁的动作
- 动作属于基础 / 战斗 / 表现中的哪一类
- 用在什么场景
- 动作整体怎么演
- 节奏和幅度是什么感觉
- 是否循环
- 是否带位移
- 是否需要配合表情 / 特效 / 武器
- 至少需要几套
- 最终怎么交付

| ------- | ---- | -------- | ------------------ | ------------------------------------------------------------ | ------------------- | -------- | ------------------ | ------------------------------------ | --------------------------- | ------------------- | ------------------------ |

## 8. 资源命名与交付规范

### 8.1 命名格式

适用：Unity + Spine | 核心：全小写 + 下划线 + 无中文无空格

**通用规则**

| 规则           | 示例                      |
| -------------- | ------------------------- |
| 全小写         | ani_dog_idle ✅            |
| 下划线分隔     | ani_boss_spawn ✅          |
| 无空格、无中文 | 主角待机 ❌                |
| 数字不开头     | 1_ani ❌ / ani_01 ✅        |
| 无特殊符号     | ani#attack ❌              |

**动作资源命名规范**

| 资源类型   | 公式                     | 示例                        |
| ---------- | ------------------------ | --------------------------- |
| 骨骼动画   | ani_角色名_动作名        | ani_dog_idle.json           |
| 序列帧动画 | ani_角色名_动作名_编号   | ani_dog_idle_001.png        |

**常用缩写**

| 缩写    | 含义   | 缩写    | 含义   |
| ------- | ------ | ------- | ------ |
| idle    | 待机   | walk    | 行走   |
| attack  | 攻击   | hit     | 受击   |
| die     | 死亡   | win     | 胜利   |
| lose    | 失败   | spawn   | 登场   |
| L       | 左侧   | R       | 右侧   |

### 8.2 输出要求

**Spine / 骨骼动画输出要求**

| #  | 要求                     | 说明                                         |
| -- | ------------------------ | -------------------------------------------- |
| 1  | 文件完整性               | .json/.asset + .atlas + .png 齐全            |
| 2  | 帧率统一                 | 项目统一帧率（如30fps）                      |
| 3  | 骨骼与部件命名规范       | 全小写+下划线，无中文                        |
| 4  | 循环动作首尾衔接         | 循环动作首帧和尾帧完全一致或自然衔接         |
| 5  | 事件标记                 | 攻击帧、落地帧、关键节点等事件已在时间轴标记 |

## 11. 自检

> AI自检

### 生成后强制自检（Fail Gate）

以下任一项不满足，则该动作-ADD 判定为"不合格，不可直接发动画制作"。

**通用项（所有ADD类型均适用）**

1. 复用入口被直接省略，未判断当前系统的展示要求
2. 新版本新增内容未同步进 ADD
3. 有参考图，但需求描述仍不足以让动画师独立开做

**动作专属项**

4. 动作需求仅写标签式名称（如"待机动作""攻击动作"），未写具体动作演绎描述
5. 动作需求未写明是否循环
6. 动作需求未写明是否带位移
7. 动作需求未写明绑定内容 / 关键节点（如需配合特效/表情）
8. 动作需求未标明归属角色和动作分类（基础/战斗/表现）
9. 存在角色在结算页有出镜，但未建立对应表现动作条目
10. 存在战斗攻击行为，但未建立受击 / 死亡动作条目

### 自检问题单（生成后逐项回答）

- 是否已建立角色与怪物清单？
- 是否已先做 ADD 覆盖总表？
- 是否每条动作都明确了归属角色？
- 是否每条动作都标注了分类（基础/战斗/表现）？
- 是否每条动作都写了用在什么场景？
- 是否每条动作都写了动作整体怎么演？
- 是否每条动作都写了循环方式？
- 是否每条动作都写了位移要求？
- 是否每条动作都写了绑定内容 / 关键节点？
- 是否存在仅写标签名（"待机动作"）而无具体描述的条目？
- 是否存在"复用，所以没写"的条目？
- 是否存在结算页角色动作遗漏的情况？
