# **一、配置体系总原则 & 分层结构（含通用层判定规则）**

## **1、配置体系核心目标**

为保证项目的可维护性、复用性与可扩展性，所有配置必须遵循以下目标：

1. **高抽象 & 少表数量**：能合并的尽量合并，通过 `type / rule_type` 等区分。
2. **通用层与玩法层严格分离**：通用层必须保持干净，不含玩法逻辑，不允许写入某个系统/玩法的专属字段。
3. **表间通过 ID 引用，不复制字段**：避免数据源分裂、逻辑散落与多点维护。
4. **玩法配置集中化**：每个玩法/系统使用独立 Excel（多 sheet），便于迭代与复用，不污染项目通用表。
5. **避免上帝表**：不把跨玩法/系统的业务规则、专属语义塞进通用表。
6. **多玩法共用统一抽象模型**：时间、阶段、条件、计数、奖励轨道、事件提示等皆可复用。

## **2、如何判断“一个表能否全项目共用”**

一个表 **满足以下 3 条 → 可归入通用层**；否则 → 必须归入玩法独立层：

1. **跨 ≥3 个系统复用同一套字段结构**
2. **新增内容只需“加行”，不需要“加字段”**
3. **字段语义跨系统一致，不绑定具体系统名词**

> 若做成通用表会出现大量“仅对某玩法有效字段/空字段”，则是上帝表风险 → 禁止通用化。

## **3、配置分层结构（必须遵循）**

### A 层：通用配置层（全项目共用，不含玩法逻辑）

通用层分为两类：**全局基础表**（主数据）与 **全局服务表**（通用能力）。

#### **A1. 全局基础表（强通用，必须共用）**

> 满足以下任意 2 条，就应当做全局基础表：
>
> - **定义了核心ID主数据**：很多系统都要引用它（`id` 会跨玩法被引用）
> - **内容与玩法无关**：不依赖某个玩法的流程、奖励、积分、阶段
> - **结构长期稳定**：一年内几乎不改字段结构
> - **不会因为新增玩法而新增字段**：新增玩法只会“新增行/新增数据”，不会“改列”

**例：**

| **能力域**     | **表名**            | **用途边界（只放基础信息）**                                 |
| -------------- | ------------------- | ------------------------------------------------------------ |
| 场景对象主数据 | object_cfg          | 场景内所有可交互对象的基础定义（NPC/怪物/Boss/采集物/资源点/据点/机关等），用 object_type 区分；只描述对象自身信息（坐标/刷新/交互方式等） |
| 物品主数据     | item_cfg            | 全项目物品静态信息（品质、icon、描述、堆叠、绑定等）         |
| 场景主数据     | scene_cfg           | 地图自身信息（地图ID、加载资源、出生点、分线基础参数等）     |
| 文本主数据     | text_cfg            | 所有文案（飘字/弹窗/公告/频道文本），统一 ID 管理            |
| 功能开启主数据 | function_unlock_cfg | 系统/入口/按钮的开启门槛（等级、任务、世界等级、服龄等）     |
| 时间主数据     | schedule_cfg        | 全游戏统一日程与重置点（每日/每周重置、开放窗口、预告窗口、icon、描述等） |

#### **A2. 全局服务表（可通用，推荐共用）**

> 提供通用规则表达/工具能力；玩法只做参数化，不改结构、不写玩法语义字段。

**例：**

| **能力域** | **表名**                            | **用途边界（只放通用表达）**                                 |
| ---------- | ----------------------------------- | ------------------------------------------------------------ |
| 条件系统   | condition_cfg / condition_group_cfg | 开启/显示/领取/触发条件表达（AND/OR），所有系统都会用“条件”，只是在填不同 cond 行 |
| 礼包       | reward_group_cfg                    | 配置奖励组合，奖励是全游戏基础设施，玩法只引用 reward_id 注意：具体玩法“哪些行为触发哪种奖励”仍然放玩法表里，但是礼包本身适合全局 |
| 排行榜     | rank_def_cfg（可选 metric_def_cfg） | 榜单口径定义：排序字段、刷新策略、展示模板、奖励绑定。榜单是通用功能，玩法只引用 rank_id、metric_id。 |

#### **通用层边界（不可侵犯）**

✅ 通用层允许：新增数据行 / 新增事件ID / 新增文案行 / 新增奖励包ID

 ❌ 通用层禁止：为玩法新增字段 / 在通用表写玩法语义字段 / 大量空字段（上帝表化）

### B 层：玩法独立配置层（每个玩法一个 Excel，多 sheet）

玩法层只描述“该玩法如何使用通用层资源”，包括但不限于： **消耗、奖励触发、流程、计分、胜负、玩法对象启用清单、专属事件映射、阶段细节。**

## **4、B层内部：主模块共享配置 与 子模块专属配置（v1.2新增，强制）**

### 4.1 目的（为什么要加这一层）
为避免“同一系统内多个子模块各写一份相同配置”导致口径分裂、字段结构不一致，本章规定：  
- **同一张配置表/同一个配置块，只允许有一个‘字段结构与约束’的唯一归属文档**；  
- 其余文档只能**引用**该归属文档，不得复制字段结构与约束。

### 4.2 概念定义（B层内再分两类）
- **B-M：主模块共享配置（主模块级）**  
  在同一模块/系统内，被多个子模块共同引用，且语义不绑定某一个子模块流程的配置表/配置块。  
  例：员工系统的“员工属性”配置，被招聘、培养、项目指派等多个子模块共同引用。

- **B-S：子模块专属配置（子模块级）**  
  仅服务某一个子模块闭环，字段语义强绑定该子模块流程/规则，对其他子模块无复用价值的配置表/配置块。  
  例：招聘模块的“候选池/刷新/招聘消耗”配置。

### 4.3 归属判定规则（强制，按顺序判定，命中即停止）
对每一张新设计的表/每一个配置块，必须按以下顺序判定：

**Step A：是否属于通用层（A层）？**  
满足“跨≥3系统复用、只加行不加字段、语义跨系统一致” → 归入A层通用配置层；禁止放入任何模块目录。

**Step B：是否属于主模块共享（B-M）？**  
满足以下任一条 → 判为B-M：
1) 在同一模块内被 **≥2个子模块**引用；  
2) 该表定义的是该模块的“核心实体/核心口径/核心枚举”，属于“先定义再引用”的上游配置（应先于依赖表产出）。

**Step C：否则为子模块专属（B-S）**  
仅被单一子模块使用，或字段语义明显绑定该子模块流程/规则 → 归入该子模块。

### 4.4 文档归属与目录规范（强制）
在 `docs/design/{模块名称}/cfg/` 下，固定如下结构：

- **主模块共享配置文档（B-M）**  
  `docs/design/{模块名称}/cfg/_main/配置-{模块名称}-主模块-配置表设计说明.v1.0.md`

- **子模块专属配置文档（B-S）**  
  `docs/design/{模块名称}/cfg/{子模块名称}/配置-{模块名称}-{子模块名称}-配置表设计说明.v1.0.md`

**硬规则：**
1) B-M 文档只定义主模块共享配置块/表结构/约束；子模块文档只能引用。  
2) B-S 文档只定义该子模块专属配置块/表结构/约束；不得重复定义 B-M 已定义内容。  
3) 同一张表/同一配置块的字段结构与约束，只允许在“唯一归属文档”出现一次；其他位置只能引用。

### 4.5 生成顺序（强制：先主后子）
当系统存在子模块拆分时，配置文档生成顺序必须为：

1) **先产出主模块共享配置（B-M）**  
   先生成/更新 `cfg/_main/…`，作为唯一口径源。

2) **再产出各子模块专属配置（B-S）**  
   每个子模块文档只定义专属表；凡需用到共享表，必须引用 B-M 文档，不得复制字段结构与约束。

### 4.6 归属变更处理（强制：提升规则）
若在编写某个子模块配置时发现某配置表/配置块被多个子模块需要：
- 该配置必须从 B-S **提升为 B-M**：迁移到 `cfg/_main/…`  
- 原子模块文档删除该表/块的字段结构与约束，仅保留引用  
- 最终保证“唯一归属”

### 4.7 示例（用于判定一致）
- **员工属性配置**：被多个子模块引用 → B-M，放 `cfg/_main/`，先生成。  
- **招聘配置**：仅招聘子模块使用 → B-S，放 `cfg/招聘/`，后生成。

# **二、玩法/系统配置标准（多 sheet） & 上帝表禁止规则**

## **1、玩法/系统独立配置标准结构（建议模板）**

每个玩法/系统应有一个独立的配置文件

例如：

- `clothes.xlsx`（时装系统）
- `store.xlsx`（店铺系统）
- `team.xlsx`（组队系统）
- `frame.xlsx`（头像框系统） 等等。

每个玩法/系统的 Excel 内部可包含多个 sheet，用于分区管理规则。

标准 sheet 列表：

| **Sheet**           | **用途**                                                     |
| ------------------- | ------------------------------------------------------------ |
| general_rules       | 本玩法的基础规则：入口、参与等级、预告、场景绑定（引用 schedule_id, unlock_id 等） |
| phase_cfg           | 流程阶段：日常/仪式/结算等                                   |
| consume_cfg         | 本玩法消耗（引用 item_id/currency_id）                       |
| score_or_metric_cfg | 本玩法计分/积分来源与公式入口（引用 object_id）              |
| reward_trigger_cfg  | 行为触发奖励（引用 reward_id/drop_id/track_id）              |
| reward_track_node   | 阶段/累计/周奖励轨道节点（引用 reward_id）                   |
| counter_bind_cfg    | 本玩法使用哪些计数器规则（引用 counter_id）                  |
| event_bindings      | 本玩法事件 → 文案/表现（引用 event_id/text_id）              |
| rank_rules          | 本玩法榜单定义（引用 rank_def_id/track_id）                  |
| map_logic           | 本玩法启用哪些 object_id、在哪些阶段可见/可交互              |

> 玩法层可以增减 sheet，但必须遵循：**一个 sheet 只管一类配置职责**，避免混杂。
>
> 玩法层只引用通用层 ID，不扩展通用表结构。

## **2、上帝表禁止规则**

任何表出现以下情况，判定为上帝表风险，必须拆分或下沉到玩法层：

1. 通用表中出现玩法专属语义字段
2. 为满足某玩法需求而新增通用表字段结构
3. 字段过多且大量字段对多数类型无效（空字段泛滥）
4. 一张表同时承担“对象+流程+奖励+条件+文案”等多职责

**禁止理由：破坏抽象、降低可复用性、影响多人协作、极难维护。**

## 3、配置设计准则（必须执行）

1. **通用表只能描述基础信息，绝不能写玩法逻辑。**
2. **每个玩法必须有独立 Excel，所有配置集中且结构化。**
3. **sheet 内按模块拆分，不用增加多个文件。**
4. **表间只允许用 ID 引用，禁止复制字段。**
5. **对象行为在玩法内定义，不在对象表中扩展字段。**
6. **复杂玩法要确保抽象可迁移，以便未来复制玩法模版。**
7. **引用的配置表不可删字段，只可新增字段**

## **4、验收要点（必须可检查）**

- 通用层是否保持纯净（新增玩法是否只加行不加字段）
- 玩法层是否集中且职责清晰（多 sheet，无混表）
- 条件/计数器/奖励轨道/事件/榜单是否复用通用能力
- 表间是否只用 ID 引用，未出现字段复制与多源维护
- 模块内是否满足“唯一归属”：同一张表/同一配置块的字段结构与约束只出现一次，其余均为引用
- 模块内是否满足“先主后子”：存在共享配置时，必须先有 cfg/_main/… 的唯一口径源，再有子模块专属配置
- 子模块配置文档是否存在“复制字段结构/重复约束”的情况：一旦发现必须提升或回收为主模块共享配置

# 三、配置表设计原则

## 1、核心原则

### 原则0：配置表是给策划用的工具，不是给程序炫技的地方

**优先级**：简洁清晰 > 配置便利 > 查询效率 > 技术优雅

**关键规则**：

- 策划配置体验优先于代码实现效率
- 除非有性能瓶颈的明确证据，否则优先可读性
- 避免为了技术优化（如O(1)查询）而牺牲配置清晰度

### 原则1：示例驱动设计（Example-Driven Design）

**禁止抽象描述，必须提供真实数据示例**

#### ❌ 错误做法

> "该字段使用JSON数组格式，只配置有值的项。"

**问题**：策划不知道具体怎么填，程序不知道具体格式。

#### ✅ 正确做法

**配置说明**：

- 格式：`[{id:int, value:int}, ...]`，每个`{}`是一项数据
- 示例：`[{3,80},{6,95}]` 表示ID=3的值为80，ID=6的值为95
- 未填写的项默认为0

**数据示例**：

```
1, 实体名称A, [{1,78},{3,80},{4,88}], ...
2, 实体名称B, [{2,65},{5,92}], ...
3, 实体名称C, [{1,80},{6,95},{10,70}], ...
```

**检查规则**：

- ✅ 必须提供3个真实数据示例（标准/边界/复杂情况）
- ✅ 必须说明"策划如何填写"
- ✅ 必须说明"未填写字段的默认值"
- ❌ 禁止只写抽象格式定义

### 原则2：自顶向下设计（Top-Down Design）

**核心实体定义表 → 依赖表 → 验证引用完整性**

#### ❌ 错误流程（Bottom-Up）

1. 先设计业务表A
2. 发现需要引用某些实体，直接在列名中硬编码实体名称
3. 发现其他表也需要引用这些实体，再补充定义表
4. 发现之前的表都硬编码了实体名称，推倒重来 ❌

#### ✅ 正确流程（Top-Down）

阶段1：识别核心实体

├─ 实体A（被多处引用）

├─ 实体B（枚举类型）✅ 优先定义

├─ 实体C（业务主体）

└─ 实体D（关联实体）

阶段2：定义核心实体表

└─ entity_B_cfg（实体B定义表）✅ 最先创建

阶段3：设计依赖表（引用核心实体）

├─ entity_A_cfg（引用entity_B_id）

├─ entity_C_cfg（引用entity_B_id）

└─ entity_D_cfg（引用entity_B_id）

阶段4：验证引用完整性

└─ 检查所有entity_B_id都能在entity_B_cfg中找到定义

### 原则3：禁止硬编码列名（No Hardcoded Column Names）

**业务实体名称只能出现在定义表的数据行中，不能出现在列名中**

#### ❌ 错误示例

## **business_table (错误版本)** | 实体ID | 实体名称 | 属性A | 属性B | 属性C | 属性D | 属性E | ... | |--------|---------|------|------|------|------|------|-----| | 1 | 业务实体1 | 高 | 低 | 中 | - | 高 | ... |

**问题**：

- ❌ 多个属性名硬编码在列名中
- ❌ 无法配置属性的元数据（描述、图标、类型等）
- ❌ 新增属性需要修改表结构
- ❌ "高"/"低"/"中"/"-"的语义不清晰

#### ✅ 正确示例

**表1：attribute_cfg（属性定义表）**

| 属性ID | 属性名称 | 属性描述        | 图标路径    | 数据类型 |
| ------ | -------- | --------------- | ----------- | -------- |
| 1      | 属性A    | 属性A的说明文本 | icon_attr_a | enum     |
| 2      | 属性B    | 属性B的说明文本 | icon_attr_b | int      |
| 3      | 属性C    | 属性C的说明文本 | icon_attr_c | float    |

**表2：business_table（业务表）**

| 实体ID | 实体名称  | 主属性ID_1 | 主属性ID_2 | 次属性ID_1 | 次属性ID_2 | ...  |
| ------ | --------- | ---------- | ---------- | ---------- | ---------- | ---- |
| 1      | 业务实体1 | 1          | 3          | 2          | 5          | ...  |

**检查规则**：

- ❌ 禁止列名出现业务实体名称
- ❌ 禁止列名出现"属性1"、"属性2"等枚举序号
- ✅ 使用`main_attr_id_1`等ID引用
- ✅ 业务实体名称只出现在定义表的数据行中

### 原则4：稀疏 vs 密集判断标准

**根据字段填充率选择配置格式**

#### 判断流程

1. 统计字段填充率 = 实际填写字段数 / 总字段数

1. 应用规则：
   1. 填充率 > 70%  → 密集格式（数组/全字段）
   2. 填充率 30-70% → 按具体情况决定
   3. 填充率 < 30%  → 稀疏格式（只配有值字段）

1. 示例验证：
   1. 创建3个典型配置示例
   2. 比较密集格式 vs 稀疏格式的行数/字段数
   3. 选择更简洁的格式

#### 格式对比

**密集格式（适用于填充率>70%）**：

[值1, 值2, 值3, 值4, 值5, 值6, 值7, 值8, 值9, 值10]

// 所有字段都需要填写，包括默认值

**稀疏格式（适用于填充率<30%）**：

[{id:3, value:80}, {id:6, value:95}, {id:10, value:70}]

// 只填写非默认值的字段

**优缺点对比**：

| **格式** | **优点**                 | **缺点**                   | **适用场景**     |
| -------- | ------------------------ | -------------------------- | ---------------- |
| 密集格式 | 查询快（O(1)），结构固定 | 冗余数据多，配置繁琐       | 大部分字段都有值 |
| 稀疏格式 | 配置简洁，无冗余数据     | 查询稍慢（O(n)），需要遍历 | 少数字段有值     |

### 原则5：主从表 vs 单表 vs JSON字段

**根据子项数量、查询需求、配置频率选择表结构**

#### 决策表

| **场景**                    | **推荐方案**         | **原因**                     |
| --------------------------- | -------------------- | ---------------------------- |
| 1对少量固定子项（1-5个）    | 单表，子项作为独立列 | 配置直观，查询简单           |
| 1对大量固定子项（6-20个）   | 单表，子项用JSON数组 | 避免列爆炸，保持单表简洁     |
| **1对动态数量子项**         | 主从表               | 子项数量不固定，需要灵活扩展 |
| **1对大量子项且需独立查询** | 主从表               | 需要对子项进行独立统计和分析 |

#### 禁用主从表的场景

- ❌ 子项数量固定且≤20
- ❌ 子项不需要独立查询和统计
- ❌ 主要用途是配置而非运营数据

#### 表结构对比

**过度拆分（主从表）**：

主表：entity_cfg (1行/实体)

从表：entity_detail_cfg (N行/实体)

总计：1+N行配置一个实体 ❌ 冗余

**合理设计（单表+****JSON****）**：

单表：entity_cfg

属性字段：json_array，值为 [{id:1, value:78}, {id:3, value:80}]

总计：1行配置一个实体 ✅ 简洁

### 原则6：全局配置 vs 明细配置分离

**主表存全局配置（1行），从表存明细配置（N行）**

#### ❌ 错误示例（混在一起）

growth_cfg (错误版本)

| 类型ID | 基础经验值 | 经验系数 | 成长速度 | 成长上限 |
|--------|-----------|---------|---------|---------|
| 1 | 100 | 1.5 | 1.0 | 999 |
| 2 | 100 | 1.5 | 1.2 | 999 |
| 3 | 100 | 1.5 | 1.5 | 999 |
... (N行，每行都重复相同的"基础经验值"和"经验系数")

**问题**：

- ❌ 全局参数在N行中重复配置
- ❌ 修改全局参数需要改N行
- ❌ 容易出现配置不一致

#### ✅ 正确示例（主从表分离）

**主表：growth_base_cfg（全局配置，1行）**

| 配置ID | 基础经验值 | 经验系数 | 小型奖励系数 | 中型奖励系数 | 大型奖励系数 |
| ------ | ---------- | -------- | ------------ | ------------ | ------------ |
| 1      | 100        | 1.5      | 1.0          | 1.5          | 2.0          |

**从表：growth_detail_cfg（明细配置，N行）**

| 类型ID | 成长速度 | 成长上限 | 衰减系数 |
| ------ | -------- | -------- | -------- |
| 1      | 1.0      | 999      | 0.8      |
| 2      | 1.2      | 999      | 0.9      |
| 3      | 1.5      | 999      | 0.85     |

### 原则7：【ID引用原则】- 永远用ID，不用文本或布尔

**❌ 错误做法**：

```Plain
employee_position_cfg:
  是否有光环: bool
  光环类型: string "程序光环/策划光环/美术光环"
```

**✅ 正确做法**：

```Plain
employee_position_cfg:
  光环ID: int (引用manager_aura_cfg, 0=无光环)

manager_aura_cfg:
  光环ID: int (主键)
  光环名称: string
```

**原因**：

- 程序员只需 `if (光环ID > 0)` 判断有无光环
- 通过ID查询完整光环配置，不需要硬编码字符串匹配
- 避免拼写错误（"程序光环" vs "程序光環"）

### 原则8：【枚举用int】- 状态/类型用数字枚举，不用字符串

**❌ 错误做法**：

```Plain
given_name_cfg:
  性别: string "男/女/通用"
```

程序员要写：`if (性别 == "男")` 或 `if (性别 == "female")` → 容易出错

**✅ 正确做法**：

```Plain
given_name_cfg:
  性别: int  枚举(0=通用, 1=男, 2=女)
```

程序员写：`if (性别 == 1)` → 清晰高效

**常见枚举场景**：

- 性别：0=通用, 1=男, 2=女
- 状态：0=待处理, 1=进行中, 2=已完成
- 职位类别：1=普通职位, 2=主职位
- 稀有度：1=普通, 2=稀有, 3=史诗, 4=传奇

### 原则9：【一表一结构】- 一个cfg只能有一种表结构

**❌ 错误做法**：

```Plain
employee_name_pool_cfg:
  姓氏表: {姓氏ID, 姓氏, 权重}
  名字表: {名字ID, 名字, 性别, 权重}  ← 两种结构混在一起
```

**✅ 正确做法**：

```Plain
surname_cfg:        {姓氏ID, 姓氏, 权重}
given_name_cfg:     {名字ID, 名字, 性别, 权重}
```

**原因**：

- 程序读表时期望统一的数据结构
- 方便扩展和维护
- 符合数据库设计第一范式

## 2、设计前准备：5个必答问题

在设计任何配置表前，必须回答以下问题：

### 问题1：谁来配置？（User Persona）

-  策划（追求直观易读）
-  程序（可接受复杂格式）
-  数值（追求公式和关系清晰）

**规则**：策划配置 > 程序配置，优先策划的使用体验。

### 问题2：配置频率？（Frequency）

-  一次性配置（如初始化数据）→ 可以复杂
-  低频调整（每月1-2次）→ 需要清晰
-  高频迭代（每天多次）→ 必须简洁

**规则**：频率越高，格式越简洁。

### 问题3：数据特征？（Data Pattern）

-  密集数据（大部分字段都有值）→ 用密集格式
-  稀疏数据（只有少数字段有值）→ 用稀疏格式
-  混合数据 → 拆分表或用JSON

**规则**：数据稀疏度 > 30%时，必须用稀疏格式。

### 问题4：查询方式？（Access Pattern）

-  随机查询（需要快速O(1)访问）→ 考虑数组下标
-  遍历查询（O(n)可接受）→ 可用稀疏结构
-  批量导入（一次性加载）→ 格式灵活

**规则**：除非性能瓶颈证据确凿，否则优先可读性 > 查询效率。

### 问题5：典型配置场景？（Use Case）

必须用具体示例说明配置流程：

**场景描述**：策划想配置实体X - 需要配置的属性：属性A=80、属性C=95、属性F=70 - 不需要配置的属性：属性B、属性D、属性E、属性G **期望配置体验**： 策划打开Excel，看到实体X这行，只需要填写3个有值的属性，不需要填写其他默认为0的属性。 **格式选择**： ❌ [0, 80, 0, 95, 0, 70, 0]  // 必须填7个，有4个0，不清晰 ✅ [{2,80}, {4,95}, {6,70}]  // 只填3个，清晰

## 4、系统级配置表设计流程

> 在进入阶段1前，必须先完成“归属判定（A层 / 主模块共享 / 子模块专属）”，并确定唯一归属与生成顺序。

### 阶段1：识别核心实体（Entity Identification）

列出系统中所有的**名词**，判断是否需要独立配置表：

**检查规则**：

- ✅ 如果某个实体有**多个属性**（≥3个字段）→ 需要独立表
- ✅ 如果某个实体会被**多处引用** → 需要独立表
- ✅ 如果某个实体有**枚举值** → 需要独立表
- ❌ 如果只是简单的**布尔标记**或**单一数值** → 不需要独立表

### 阶段2：绘制引用关系图（Reference Diagram）

画出配置表之间的引用关系：

core_entity_cfg (核心实体定义表)

​    ↑

​    │ 引用core_entity_id

​    │

​    ├── business_table_A (业务表A)

​    │       - main_entity_id_1/2/3 引用 core_entity_id

​    │

​    ├── business_table_B (业务表B)

​    │       - entity_id 引用 core_entity_id

​    │

​    └── business_table_C (业务表C)

​            \- config [{entity_id, value}] 引用 core_entity_id

**检查规则**：

- ✅ 所有ID字段必须能找到对应的定义表
- ✅ 引用链条不能断裂（如果A引用B，B必须存在）
- ❌ 避免循环引用（A引用B，B又引用A）

### 阶段3：设计核心定义表（Core Definition Tables）

**最先设计被引用最多的核心实体表**

**示例：core_entity_cfg（核心实体定义表）**

| **字段名**   | **类型** | **说明**   | **示例值**      |
| ------------ | -------- | ---------- | --------------- |
| 实体ID       | int      | 唯一标识   | 1               |
| 实体名称     | string   | 显示名称   | 实体A           |
| 实体描述     | string   | 说明文本   | 这是实体A的描述 |
| 图标资源路径 | string   | UI图标路径 | icon_entity_a   |
| 排序权重     | int      | UI显示顺序 | 1               |

**数据示例**：

1, 实体A, 这是实体A的描述, icon_entity_a, 1

2, 实体B, 这是实体B的描述, icon_entity_b, 2

3, 实体C, 这是实体C的描述, icon_entity_c, 3

### 阶段4：设计依赖表（Dependent Tables）

**引用核心定义表的ID字段**

**示例：business_table（业务表）**

| **字段名**     | **类型** | **说明**                | **示例值** |
| -------------- | -------- | ----------------------- | ---------- |
| 业务ID         | int      | 唯一标识                | 1          |
| 业务名称       | string   | 显示名称                | 业务实体1  |
| **主实体ID_1** | **int**  | **引用core_entity_cfg** | **1**      |
| **主实体ID_2** | **int**  | **引用core_entity_cfg** | **3**      |
| **次实体ID_1** | **int**  | **引用core_entity_cfg** | **2**      |

**数据示例**：

1, 业务实体1, 1, 3, 2, 5, ...

### 阶段5：验证引用完整性（Reference Integrity）

**检查所有引用的ID都能在定义表中找到**

验证脚本伪代码：

for each table in dependent_tables:

​    for each row in table.rows:

​        for each field in row.reference_fields:

​            if field.value not in core_table.ids:

​                raise Error("引用断裂: {table}.{field} = {value} 在 {core_table} 中不存在")

## 5、配置表设计反模式

### 反模式1：缺少核心定义表（Missing Core Definition Table）

#### ❌ 错误示例

| 业务ID | 业务名称 | 实体A | 实体B | 实体C | 实体D | 实体E | ...  |
| ------ | -------- | ----- | ----- | ----- | ----- | ----- | ---- |
| 1      | 业务1    | 高    | 低    | 中    | -     | 高    | ...  |

**问题**：

- ❌ 多个实体名硬编码在列名中
- ❌ 无法配置实体的元数据（描述、图标等）
- ❌ 新增实体需要修改表结构

#### ✅ 正确做法

1. 创建`entity_cfg`定义所有实体
2. 业务表使用`main_entity_id_1/2/3`引用

### 反模式2：主从表混用全局配置（Mixing Global Config）

#### ❌ 错误示例

| 类型ID                     | 全局参数A | 全局参数B | 个性化参数C | 个性化参数D |
| -------------------------- | --------- | --------- | ----------- | ----------- |
| 1                          | 100       | 1.5       | 1.0         | 999         |
| 2                          | 100       | 1.5       | 1.2         | 999         |
| ... (N行，全局参数重复N次) |           |           |             |             |

**问题**：全局参数在N行中重复配置

#### ✅ 正确做法

拆分为主从表：

- 主表：`base_cfg`（1行，全局配置）
- 从表：`detail_cfg`（N行，个性化配置）

### 反模式3：过度拆分主从表（Over-Normalized）

#### ❌ 错误示例

主表：entity_cfg (1行/实体)

从表：entity_detail_cfg (N行/实体，N为固定值≤20)

总计：1+N行配置一个实体

**问题**：固定数量的子项拆成主从表，配置冗余

#### ✅ 正确做法

单表 + JSON字段：

entity_cfg: 1行/实体，子项用json_array存储

**判断标准**：

- 子项数量固定且≤20 → 单表 + JSON字段
- 子项数量动态且需独立查询 → 主从表

### 反模式4：稀疏数据用密集格式（Dense Format for Sparse Data）

#### ❌ 错误示例

实体配置：[0, 80, 0, 0, 95, 0, 70, 0, 0, 0]

// 填充率：3/10 = 30%，但必须填10个值，含7个无意义的0

#### ✅ 正确做法

实体配置：[{2,80}, {5,95}, {7,70}]

// 只填3个实际有值的项

### 反模式5：用抽象描述代替具体示例（Abstract over Example）

#### ❌ 错误做法

> "该字段使用JSON数组格式，策划只需配置有值的项。"

**问题**：策划不知道具体怎么填

#### ✅ 正确做法

**配置说明**：

- 格式：`[{id, value}, ...]`
- 示例：`[{3,80},{6,95}]` 表示ID=3的值为80，ID=6的值为95
- 未填写的项默认为0

**数据示例**：

1, 实体A, [{1,78},{3,80},{6,95}], ...

2, 实体B, [{2,65},{4,88}], ...

## 7、快速参考卡片

### 设计配置表前，先问自己：

1. ✅ **是否跨子模块共享？** → 若同模块内≥2子模块引用，则归主模块共享配置（B-M），先生成再被引用
2. ✅ **谁配置？** → 策划 > 程序，优先策划体验
3. ✅ **多久配？** → 频率越高，格式越简洁
4. ✅ **数据密还是稀？** → 填充率<70%用稀疏格式
5. ✅ **怎么查询？** → 除非瓶颈，优先可读性>效率
6. ✅ **有示例吗？** → 必须3个真实数据示例

### 设计流程

识别核心实体 → 设计核心定义表 → 设计依赖表 → 验证引用完整性 → 提供3个示例

### 绝对禁止

- ❌ 列名硬编码业务实体名称
- ❌ 用抽象描述代替具体示例
- ❌ 稀疏数据用密集格式
- ❌ 缺少核心定义表
- ❌ 主从表混用全局配置

### 黄金法则

> **配置表是给策划用的工具，不是给程序炫技的地方。**
>
> **优先级：简洁清晰 > 配置便利 > 查询效率 > 技术优雅**
